What I did today

Today we learn about environments and why the same code can give different results on two different computers.

The environment we looked at is called Pixi.

Why do we use environments?

An environment keeps each project separate. It also means someone else can rebuild the exact same setup on their own computer.

Installing Pixi

One line in the terminal:

wget -qO- https://pixi.sh/install.sh | sh

Starting a project

Make a new environment for the project:

pixi init lina_pixi_training -c conda-forge -c bioconda

The -c parts say where to download software from.

This creates two files:

  • pixi.toml — the short, readable one. It lists the project name and the tools I asked for. This is the file I actually edit.
  • pixi.lock — the long, automatic one. It records the exact versions and where they came from. I never edit this by hand, but it is the file that makes the setup truly reproducible.

Quality control

Before analysing sequencing data, we check whether the data is any good. Bad data gives bad results, no matter how careful the analysis is. Problems come from contamination, handling mistakes, or the sequencing machine itself.

What the raw data looks like

Sequencing data comes in FASTQ files. Every read takes four lines:

  1. The read name, starting with @
  2. The sequence itself
  3. A + separator
  4. The quality scores, one character per base

The fourth line is the important one. Each character is a score from 0 to 42 saying how sure the machine was about that base. Low scores mean the base might be wrong.

FastQC

FastQC checks the quality of a whole file at once, so we do not have to look at millions of reads by hand.

We add it to the Pixi environment, not to the whole computer:

pixi add fastqc
pixi run fastqc --help

Running it on the cluster

Big files take time, so the work runs on a cluster instead of a laptop. The cluster uses SLURM to decide who runs what and when. We ask for an account, some time, and a number of cores:

srun -A project_ID -t 15:00 -n 1 pixi run fastqc

For more than one sample it is easier to put the same settings into a small script and submit it:

sbatch fastqc.sh

The script is also a record of exactly what was run, which is the reproducible part.

MultiQC

One report per sample adds up quickly. MultiQC collects them all into a single report, so the whole dataset can be checked in one place.

Keeping the session alive

If the connection to the cluster drops, the job dies with it. screen keeps it running:

screen -S fastqc     # start a session
# Ctrl + a, then d   # leave it running
screen -r fastqc     # come back to it later

Containers

Pixi makes sure we install the same tools. A container goes one step further: it packs the tools and the operating system around them into a single file. That file behaves the same way on a laptop, on a server, or on someone else’s computer years from now.

Containers help when:

  • people in the group use different operating systems
  • two tools need different versions of the same dependency
  • old software will not install on a modern system

Which container tool

  • Apptainer — for shared servers and clusters (it used to be called Singularity)
  • Docker — for a personal machine

Ready-made images are kept on Docker Hub and Seqera. It is safer to pick a popular image from a trusted maker, such as biocontainers.

Getting an image

apptainer pull name.sif docker://repository/image:version

The .sif file that comes out is the container. Naming it with the tool and version keeps things clear later.

Running it

Run a single command inside the container:

apptainer exec image.sif tool --version

Or step inside and work there:

apptainer shell image.sif

A container cannot see our files by default. -B outside:inside makes a folder on the computer visible inside the container.

run and exec are not the same: run first executes the container’s own start-up script, while exec skips it and runs exactly the command we give.

Building our own

If no ready-made image exists, we describe one in a .def file: which operating system to start from, what to install (%post), which paths to set (%environment), and what to run by default (%runscript). Then:

apptainer build output.sif definition.def

Container or Pixi?

Pixi pins the tools. A container pins the whole system around them. Containers are bigger and slower to make, but more complete, so they suit sharing a finished pipeline or rescuing software that refuses to install.
