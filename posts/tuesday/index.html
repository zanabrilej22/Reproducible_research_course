What we did today

In the morning we learned about software environments and the environment manager Pixi. In the afternoon we used Pixi on the HPC2N cluster to run a quality control (QC) of an RNA-seq dataset with FastQC, and summarised all the reports with MultiQC.

1. Why do we need environments?

It makes pipline more reproducible. Different computers have different operating systems and different versions of tools. If my FastQC version is different from yours, we might get different results.

An environment is a separate box that contains exactly the tools and versions a project needs. The tools are installed inside the environment, not on the whole computer. Each project gets its own environment, so projects never mess with each other.

2. Pixi basics

Install Pixi (once per user)

wget -qO- https://pixi.sh/install.sh | sh
source ~/.bashrc    # reload the shell so the "pixi" command is found (on Mac: ~/.zshrc)

Create an environment

pixi init zana_pixi_training -c conda-forge -c bioconda
cd zana_pixi_training
  • -c adds a channel, a trusted place Pixi is allowed to download tools from.
  • The order matters: conda-forge first, then bioconda.

This creates a file called pixi.toml:

pixi.toml
[workspace]
channels = ["conda-forge", "bioconda"]   # where tools come from
name = "zana_pixi_training"              # name of the environment
platforms = ["linux-64"]                 # operating system(s)
version = "0.1.0"

[tasks]                                  # (not used in this course)

[dependencies]                           # tools installed in the environment

Add tools and run them

pixi add quarto           # install a tool into the environment 
pixi add --help           # every command has a help page
pixi run quarto --help    # run a tool from the environment

After pixi add, a second file appears: pixi.lock. It records the exact version and source of every package.

ImportantNever delete pixi.toml or pixi.lock

Together they are the environment. pixi.toml says what I asked for, pixi.lock says exactly what was installed. Sharing these two files lets anyone rebuild the same environment.

Notepixi shell

On a normal computer, pixi shell “enters” the environment so tools can be used without typing pixi run every time (exit to leave). This does not work on HPC2N, so there I always used pixi run.

3. screen: keep working when I disconnect

screen opens a terminal session on the server that keeps running even if my laptop goes to sleep or I lose connection.

screen -S fastqc      # start a new session called "fastqc"
# Ctrl + a, then d     -> detach (leave it running in the background)
screen -ls            # list my sessions
screen -r fastqc      # go back into the session
exit                  # inside a session: close it for good

4. Setting up the project

It is important that we keep the folder organized. Raw data goes in data/, and I should never change it. Instead of copying the large files, I make symbolic links (shortcuts) to the shared course data:

mkdir -p rnaseq/data
cd rnaseq/data
ln -s /path/to/repbio26/common_data/RNAseq/*fastq.gz .
cd ..

5. The FASTQ format

Sequencing reads are stored in FASTQ files. Each read takes 4 lines:

  1. @ + the read name
  2. the DNA sequence
  3. a + (sometimes followed by the name again)
  4. the quality of each base, one character per base

To look at the first reads of a (compressed) file on the server:

zcat data/SRR5223504_1.fastq.gz | head -n 8

6. FastQC in a Pixi environment

FastQC is not installed on the server (fastqc: command not found), so I made an environment for it inside my project folder:

pixi init -c conda-forge -c bioconda
pixi add fastqc
pixi run fastqc --help

Running a job with SLURM

On a cluster, I must not run heavy work on the login node. Instead I ask the job scheduler SLURM for resources. SLURM needs to know:

  • -A which project pays for the computing time
  • -t how long the job may run (e.g. 15:00 = 15 minutes)
  • -n how many cores

Option 1: srun, quick, for one command:

mkdir fastqc
srun -A <project_ID> -t 15:00 -n 1 pixi run fastqc --noextract -o fastqc \
     data/SRR5223504_1.fastq.gz data/SRR5223504_2.fastq.gz

Option 2: sbatch, a script I can save and reuse. This is better for reproducibility, because the script is a record of exactly what I ran.

scripts/fastqc.sh
#! /bin/bash -l
#SBATCH -A <project_ID>
#SBATCH -t 30:00
#SBATCH -n 1

pixi run fastqc -o ../fastqc --noextract ../data/*fastq.gz
cd scripts
sbatch fastqc.sh                 # submit the job
squeue -u <username>             # check if it is waiting (PD) or running (R)
less slurm-<jobID>.out           # read the log when it's done (q to quit)

Project structure at this point:

rnaseq/
├── data/            # symbolic links to the raw fastq.gz files
├── fastqc/          # one .html + one .zip report per fastq file
├── pixi.lock
├── pixi.toml
└── scripts/
    └── fastqc.sh

To look at a report, right-click the .html file in the VS Code file explorer and choose Download.

7. MultiQC: one report for all samples

Opening eight separate FastQC reports gets tedious. MultiQC collects them into one report.

pixi add multiqc
scripts/multiqc.sh
#! /bin/bash -l
#SBATCH -A <project_ID>
#SBATCH -t 15:00
#SBATCH -n 1

pixi run multiqc ../fastqc -o ../multiqc
sbatch multiqc.sh

The result is multiqc/multiqc_report.html.

TipReading the report

Some “failed” modules are normal for RNA-seq. For example, Per base sequence content often fails at the start of the reads because of random-primer bias, and Sequence duplication is high because highly expressed genes produce many identical reads. Always check whether a warning is expected for the type of data.
